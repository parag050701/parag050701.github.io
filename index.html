Featured: Sanshodhak, knowledge-graph retrieval for research papers

Python · FAISS · BM25 · NetworkX · NVIDIA NIM embeddings and reranking · GROBID  |  Team project with Sarvadnya Bhatlawande, Akshat Shaha and Ajay Sawandkar, advised by Prof. Sangita Lade · 2025–26

Sanshodhak answers questions over a collection of research papers. My question was narrow: does adding a knowledge graph to retrieval help, or is dense vector search already good enough?

The system

Papers are parsed with GROBID and split into chunks: 163 papers, 4,333 chunks. Each query goes through three retrieval channels:

  1. BM25 for exact terms such as method names, datasets and acronyms.
  2. Dense retrieval over a FAISS index of 2048-dimensional NVIDIA NIM embeddings.
  3. Graph expansion over a paper graph. Two papers are linked if one cites the other, or if their vocabularies overlap strongly (Jaccard similarity ≥ 0.30). The search starts from the papers the first two channels found and pulls in their neighbours.

The three ranked lists are merged with reciprocal rank fusion (k = 60) and reranked with a cross-encoder. One design choice mattered: slot reservation. Plain fusion lets the two text channels crowd out graph results, because they agree with each other. So a quarter of the final top-k (at least one slot) is kept for graph-expanded chunks. Without it, the graph rarely got a chance to contribute anything.

Evaluation: the first benchmark was broken

The first 100-question test set gave suspiciously low scores. When I checked it question by question, 50 of the 100 questions had no answer in the corpus. Their paper identifiers didn't match the indexed papers, so no system could have scored on them. I rebuilt the test set so that each question targets one specific paper that is actually in the corpus (100 questions, 100 different target papers). Every result below uses the rebuilt set.

On this benchmark the graph helps, and each added channel helps. The cost is about 4× the latency of dense-only search. Adding BM25 to dense search did almost nothing on its own, which I didn't expect.

The experiment I reverted

To close the gap further, I replaced simple neighbour expansion with query-biased personalised PageRank, added a graph-centrality boost after reranking, and added LLM query expansion. Each of these is a common GraphRAG technique. Together they made things worse:

  • Graph-only NDCG@10 fell from 0.891 to 0.824, and it lost 6 questions it had been answering correctly.
  • The full system dropped slightly (0.917 → 0.913).
  • Latency more than doubled (1.8 s → 4.2 s for the full system).

Why: most of the graph's edges are citations, and PageRank rewards papers that many others cite. But each benchmark question targets one specific paper, often a peripheral one. So the centrality signal pushed the right answer down in favour of well-known hubs. Query expansion added 2–3 seconds per query and diluted questions that were already specific.

I reverted all three changes. I kept the code and its unit tests, because I think they fit a different benchmark. That leads to the open question.

What I'd do next

The benchmark decides which graph technique looks good. With single-paper questions, centrality hurts. With multi-hop questions, whose answers span two or three connected papers, central nodes should be the right ones. The next step is a multi-hop test set, so the graph methods are judged on the kind of question they're built for. More broadly, I'd like to understand how to build evaluations that match what users actually ask, not what is easiest to generate.

Other work

  1. SolarKey: monitoring platform for solar power plants (Mar–Sep 2026 · Python, FastAPI, Celery, PostgreSQL, Redis, Next.js, AWS)
    I built this from zero to a production system monitoring three solar plants in Maharashtra, with telemetry every 5 minutes. I also built an MCP server with 9 tools that lets LLM clients query the team's root-cause-analysis engines (the engines themselves were built by a teammate). The rule I cared most about: when the data can't support an answer, the tool returns an explicit CANNOT_CHECK instead of a plausible-looking number, and the LLM is shown that refusal rather than given something to fill the gap with. Another lesson: four dashboards were silently showing "all clear". I traced all four to the same cause, database tables that had readers but no process writing to them. The product is live at api.solar-key.com. It opens on a login page, since it serves real plant operators.

  2. Sanjaya: surveillance video as a queryable knowledge graph (with Sarvadnya Bhatlawande · 1st Prize, Impetus PICT InC 2026)
    Hours of CCTV footage are hard to search. Sanjaya turns footage into something you can ask questions about, like "when did a person enter through the side gate?" YOLOv8 detection and tracking pick out the frames where something happens. A vision-language model describes those frames, and its descriptions are checked against what the detector actually saw, which keeps it from describing objects that aren't there. The people, objects, places and events go into a knowledge graph. Questions in plain language are answered by searching the graph and a vector index together.
